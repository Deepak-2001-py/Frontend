Doc 1 · Database Design Document — six DynamoDB tables + one log table
Multi-table design (one table per aggregate) with an adjacency-list inside CLASSES for memberships. Every FK is a plain attribute holding another table's PK — joins happen in the λ handler via GSI query, never a scan.
T1 — USERS
PK / SKUSER#<userId> / PROFILE
GSI1EMAIL#<email> — login-time profile lookup
holdsprofile, role, accountStatus, cognitoSub
Referenced by every other table (teacherId, studentId, userId, actorId).
T2 — CLASSES (+ member rows)
PK / SKCLASS#<classId> / METADATA
member rowSK = MEMBER#<studentId> (the enrollment itself)
GSI1USER#<studentId> / CLASS#<classId> — "my classes"
FKteacherId → T1 (one owning teacher)
M:N students↔classes lives here — no separate MEMBERSHIPS table needed.
T3 — ASSIGNMENTS
PK / SKASSIGN#<assignmentId> / METADATA
GSI1CLASS#<classId> / DUE#<dueAt> — class feed, sorted by due date
FKclassId → T2 · qpId → T4
status: draft → open → closed → published.
T4 — QUESTION_PAPERS (+ question rows)
PK / SKQP#<qpId> / METADATA
question rowSK = Q#<qNo> — one row per parsed question
FKassignmentId → T3 (1:1) · rawS3Key / parsedS3Key → S3
Big blobs (PDF, parsed.json, rubric.json) stay in S3 — DDB holds keys + status only.
T5 — SUBMISSIONS
PK / SKSUB#<submissionId> / METADATA
GSI1ASSIGN#<assignmentId> / USER#<studentId> — teacher's grading grid
GSI2USER#<studentId> / SUBMITTED#<ts> — "my submissions"
FKassignmentId → T3 · studentId → T1
One item per (assignment, student) — GSI1 key pair enforced unique by conditional write.
T6 — RESET_REQUESTS
PK / SKRESET#<requestId> / METADATA
GSI1STATUS#<status> / <createdAt> — admin pending queue
FKuserId → T1
T7 — AUDIT_LOG (append-only)
PK / SKAUDIT#<yyyy-mm> / <ts>#<eventId>
FKactorId, targetId → T1 (soft — never queried by GSI)

Doc 3 · Data Dictionary — every ID and attribute defined
ID definitions — all IDs are ULIDs (sortable, no coordination) behind a typed prefix
userId — USER#01J… · immutable; Cognito sub stored alongside, never used as PK
classId — CLASS#01J… · minted by λ class-admin
assignmentId — ASSIGN#01J… · minted on create (draft)
qpId — QP#01J… · minted when teacher requests QP upload
submissionId — SUB#01J… · minted on upload request; unique per (assignmentId, studentId)
requestId — RESET#01J… · minted by unauthenticated λ reset-request
eventId — 8-char random suffix on <ts> · uniqueness inside a ms
S3 keys — subs/<aid>/<sid>/<file> · qp/<qpId>/<file> · never guessable-public, presigned only
timestamps — ISO-8601 UTC strings, sortable lexicographically

Doc 4 · Data Flow Diagram — upload → parsing → grading → results
1 · UPLOAD
(student)
Student picks assignment · POST /assignments/{id}/submissions → membership check → SUBMISSIONS «upload_requested» → presigned URL → direct PUT → S3 raw.pdf → S3 event → «uploaded»
2 · OCR
DDB stream → λ ocr → Textract → S3 ocr.json → «ocr_done» → student reviews text, fixes misreads → S3 corrected.json → «corrected»
3 · GRADE
(auto)
cond. write «grading_triggered» → λ grade → Bedrock reads corrected.json + QP rubricItems → per-question scores → S3 report.json → «ai_graded» + score · low confidence → SQS review queue «flagged»
4 · REVIEW
(teacher)
Teacher works the queue · per-question override + comment → report.json v2 → «overridden» + overriddenBy · every override also → AUDIT_LOG grade_overridden
5 · RESULTS
Teacher clicks Publish (whole assignment) → batch update → all SUBMISSIONS «published» · ASSIGNMENT «published» → SNS → student email/push → results screen reads report.json via GET /submissions/{id}/report
Invariant: S3 holds the artifacts (raw.pdf → ocr.json → corrected.json → report.json), DynamoDB holds the state machine. Status is only ever advanced by conditional writes, so a replayed event can't move a submission backwards.
Doc 5 · API Specification — REST over API Gateway, Cognito-JWT authorized
Auth: every route (except reset-request) requires Authorization: Bearer <idToken>. The Cognito authorizer validates the JWT; the route table below enforces the role claim; λ handlers add row-level checks (class membership, PK ownership). Login/refresh go straight to Cognito via SDK — no custom endpoint.
